## 1. What this is

A take-home interview solution (spec ID **SI26_P06**) for a university
placement team. It compares **one** student's academic profile against
**five fixed, hard-coded** career-fair roles and reports, per role, whether
the student is eligible and — if not — **every** rule that failed.

The full specification lives at `../SI26_P06-Career-Fair-Eligibility-Shortlist.md`.
**The spec is the authority.** When the spec and this file disagree, the spec
wins; when code and spec disagree, that is a bug in the code.

Interview framing matters for how you should help: the grading criteria
reward a small, reliable, fully-explainable solution. Spec §23 explicitly
penalises over-engineering. So:

- **Do not** add a backend, database, auth, external API, job feed, ORM,
  state-management library, or extra framework.
- **Do not** add ranking or scoring. This is eligibility only (spec §23).
- **Do not** create a second eligibility implementation anywhere (spec §14).
- Prefer the smallest change that satisfies the spec clause at hand.

## 3. Architecture — the one rule that matters

```
eligibility.py   ← ALL business rules. Pure. No UI imports. No I/O.
      │
      ├── app.py        Streamlit UI      (renders state only)
      ├── cli.py        terminal report   (renders state only)
      └── tests/        four suites
```

The three modules sit **flat at the project root** — no `src/`, no package,
no `__init__.py`. At this size that is a deliberate choice, not an oversight:
`import eligibility` needs no packaging concepts to explain or defend.
`conftest.py` puts the project root on `sys.path`, so test modules import
plainly (`import eligibility`, `import cli`) with no per-file path preamble,
and `pytest.ini` pins discovery to `tests/`. `pytest` therefore works from the
project root, its parent, or `tests/` itself.

Generated output lives in `docs/evidence/` and is regenerated by re-running
the commands in §6 — never hand-edit it.

`eligibility.py` is **pure**: deterministic, no side effects, no framework
imports. Both front ends import from it and neither re-implements a rule.
This is what makes the logic unit-testable without a browser and guarantees
the UI and CLI can never disagree.

**The invariant: business rules change in `eligibility.py` and nowhere else.**
If you find yourself writing a comparison, a threshold, a sort key, or a
failure string inside `app.py` or `cli.py`, stop — it belongs in
`eligibility.py`.

### Public API of `eligibility.py`

| Name | Purpose |
|---|---|
| `Role` | frozen dataclass; one role's requirements. Branches stored pre-casefolded. |
| `StudentProfile` | dataclass of **five raw strings** (unparsed, as typed) |
| `RoleResult` | `role_id`, `title`, `eligible`, `reasons` |
| `ROLES` | the five fixed roles, in spec order (CF01…CF05) |
| `SAMPLE_PROFILE` | the built-in profile from spec §2 |
| `normalize_token(s)` | `.strip().casefold()` — the comparison key |
| `parse_skills(raw)` | split on commas, trim, drop blanks, collapse dupes |
| `validate_profile(p)` | → list of error codes, `[]` when valid |
| `evaluate_role(...)` | one role → one `RoleResult` |
| `evaluate_all(p)` | → sorted `[RoleResult]`, or **`None` if invalid** |
| `counts(results)` | → `(eligible, ineligible)`, or `(None, None)` for `None` |

`StudentProfile` deliberately holds **strings, not parsed numbers**, because
validation is a spec requirement with its own error codes — parsing at the
boundary would throw away the distinction between "blank" and "10.5".

`evaluate_all` returning `None` (not an empty list) for an invalid profile is
load-bearing: it is what lets callers clear results rather than render zero
rows, satisfying spec §8.

## 4. The rules, exactly as specified

### The five roles (spec §3) — fixed local data, never fetched

| ID | Title | Branches | Min CGPA | Grad years | Max backlogs | Skills |
|---|---|---|---:|---|---:|---|
| CF01 | Data Operations Intern | CSE, IT | 7.5 | 2027 | 1 | Python, SQL |
| CF02 | QA Automation Intern | CSE, ECE, IT | 7.0 | 2027, 2028 | 1 | Git |
| CF03 | Embedded Systems Intern | ECE, EEE | 7.5 | 2027 | 1 | Git |
| CF04 | Machine Learning Intern | CSE, IT | 8.5 | 2027 | 1 | Python |
| CF05 | Platform Engineering Intern | CSE, ECE | 7.0 | 2026 | 0 | Docker, Git |

Built-in profile (spec §2): **CSE, 8.1, 2027, 1 backlog, "Git, Python, SQL"**
→ CF01 & CF02 eligible; CF03, CF04, CF05 ineligible. **2 eligible, 3 ineligible.**

### Eligibility (spec §5) — all five must pass

branch ∈ allowed · cgpa **≥** min · grad year ∈ allowed · backlogs **≤** max ·
every required skill present. Note `≥` and `≤`: CGPA exactly at the minimum
and backlogs exactly at the maximum both **pass**.

### Failure reasons (spec §9) — order is part of the contract

Every role is evaluated **independently**, with **no short-circuiting**. An
ineligible role lists *every* failed rule, each exactly once, in this order:

1. `BRANCH_NOT_ALLOWED`
2. `CGPA_BELOW_MINIMUM`
3. `GRADUATION_YEAR_NOT_ALLOWED`
4. `TOO_MANY_ACTIVE_BACKLOGS`
5. `MISSING_SKILL: <skill>` — multiple sorted **case-insensitively**
   (`AWS`, `Docker`, `GitHub Actions`)

An eligible role has an empty `reasons` list. **Do not stop at the first
failure** — spec §23 calls that out as a specific failure mode.

### Normalization (spec §6)

Branches and skills are trimmed and compared case-insensitively
(`" Python "` == `"python"` == `"PYTHON"`). Skill strings split on commas,
blank pieces dropped, duplicates collapsed case-insensitively, first spelling
and first-seen order kept.

**No inference, ever** — no aliases, no related branches, no synonyms.
`"Python"` and `"PyTorch"` are different skills. Do not add fuzzy matching.

### Validation (spec §7) — codes are exact strings

| Field | Valid when | Code on failure |
|---|---|---|
| Branch | non-blank after trim | `INVALID_BRANCH` |
| CGPA | finite, `0 ≤ x ≤ 10` | `INVALID_CGPA` |
| Graduation year | whole number, `2000–2100` | `INVALID_GRADUATION_YEAR` |
| Active backlogs | whole number, `≥ 0` | `INVALID_BACKLOG_COUNT` |

"Finite" is load-bearing: `float("NaN")` and `float("Infinity")` parse fine in
Python, so `math.isfinite()` is checked explicitly. Fields are validated
**independently**, so all problems surface at once, in the table's order.

Distinguish two different things: **2029 is a *valid* year that no role
accepts** → `GRADUATION_YEAR_NOT_ALLOWED` (an eligibility failure).
**2029.5 is an *invalid* year** → `INVALID_GRADUATION_YEAR` (a validation
error that blocks evaluation entirely).

### Result ordering (spec §10)

Eligible roles first, then ineligible. Within each group: title ascending
**case-insensitively**, ties broken by role ID ascending. One sort key:

```python
results.sort(key=lambda r: (0 if r.eligible else 1, r.title.casefold(), r.role_id))
```

`.casefold()` is required, not cosmetic: a plain ASCII sort puts `"Banana"`
before `"apple"` because uppercase sorts first.

### Invalid input clears everything (spec §8, §23)

If any field is invalid: clear results, clear both counts, show the code.
**Never leave stale results visible.** Spec §23 names this explicitly.

## 5. UI state model — read this before touching `app.py`

Streamlit re-runs the whole script on **every** keystroke. The naive approach
(write results into session state on Evaluate, render them below) leaves stale
results on screen when a field is later edited — a real spec §8 violation that
existed here and was fixed.

The fix: `app.py` **derives** display state on each run and never mutates
session state outside the Evaluate branch.

- Pressing **Evaluate** stores the results *and a snapshot* of the profile it
  evaluated (`evaluated_profile`).
- Every rerun compares the live widget values against that snapshot.

Four states, at [app.py:115-123](app.py#L115-L123):

| State | When | Shows |
|---|---|---|
| `idle` | nothing evaluated yet | prompt; no counts |
| `valid` | live profile **==** snapshot | results + counts |
| `invalid` | changed **and** a field is invalid | error code; **no** results/counts |
| `stale` | changed but all fields valid | "click Evaluate"; **no** results/counts |

Reverting an edit back to the evaluated values returns to `valid` and shows
its results again — because the comparison is against the snapshot, not a
one-way "dirty" flag.

**If you edit `app.py`, keep this derived-state discipline.** Writing
`st.session_state["results"]` from anywhere other than the Evaluate branch
re-opens the stale-state bug. Two regression tests guard it:
`test_invalid_edit_clears_results_before_evaluate_is_pressed` and
`test_editing_to_a_new_valid_value_withholds_results_until_evaluate`.

Other `app.py` mechanics worth knowing:

- **Button actions run before widgets.** Streamlit forbids writing a widget's
  `session_state` key after that widget renders, so Load Sample / Reset set
  `_pending_action` and call `st.rerun()`; the flag is consumed at the top.
- **Load Sample and Reset are intentionally identical.** Spec §13 defines
  reset as "built-in profile and role list restored", so both load
  `SAMPLE_PROFILE`. This is a deliberate spec reading, not a copy-paste slip.

## 6. Commands

```bash
cd career_fair_shortlist
pip install -r requirements.txt

python -m streamlit run app.py     # UI at http://localhost:8501
pytest -q                          # 157 tests, ~9s
pytest tests/test_eligibility.py -q   # logic only, ~0.03s — use while iterating

python cli.py                      # built-in profile report
python cli.py --cgpa 8.5           # omitted flags keep their sample value
```

`cli.py` **overlays** supplied flags onto `SAMPLE_PROFILE`, so one flag means
one change — `--cgpa 8.5` *is* spec Test 5. An explicit `--branch ""` is
honoured rather than defaulted, keeping the `INVALID_BRANCH` path reachable.

answer different questions. UI tests need no browser; `AppTest` runs the real
script and clicks real buttons.

**Run `pytest -q` after any change.** The suites encode the spec's exact
strings and orderings, so a "harmless" tidy-up that reorders reasons or
changes a code will fail loudly — which is the point.
